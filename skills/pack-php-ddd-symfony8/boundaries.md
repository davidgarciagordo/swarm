# boundaries — php-ddd-symfony8

What is NEVER touched. Applies to EVERY leaf with `Write`/`Edit` (`implementer`, `test-writer`,
`quality-fixer`, `migration-engineer`, `doc-writer`) and to any automatic `--fix`. If your task
seems to require touching something on this list, your verdict is `BLOCKED <which boundary and why>`
— you don't touch it "just a little."

## Never edited by hand

| path / pattern | why |
|---|---|
| `vendor/` | generated by `composer`; any edit is lost on the next `install` |
| `node_modules/`, `public/build/`, `public/bundles/` | build/asset artifacts |
| `var/` (`var/cache/`, `var/log/`, tool caches) | ephemeral state; deleting it is valid, editing it isn't |
| generated Doctrine proxies and metadata | regenerated; editing them masks the real bug |
| `composer.lock`, `package-lock.json` | written by the package manager; editing by hand corrupts the resolution tree |
| `.env`, `.env.local`, `config/secrets/` | real secrets; never read to quote them nor rewritten |
| `migrations/Version*.php` ALREADY APPLIED | see below |

## Already-applied migrations: added to, never edited

A migration that has already run in any environment is immutable history. Check first with the
`migrate-status` key from `commands.md`. Fixing a wrong schema = **a new migration**
that corrects it going forward. Editing an already-executed `VersionXXXXXXXXXXXXXX.php` leaves
existing databases in a state no tool can reconcile.

Also: an agent **never applies** migrations against a real database. The `migrate-up` key in
`commands.md` is `--dry-run` on purpose. Applying is the owner's decision.

## Layer rules (enforced by `deptrac` if the repo has it)

- `Domain/` doesn't depend on `Application/`, `Infrastructure/`, Symfony or Doctrine.
- `Application/` depends on `Domain/`, never on `Infrastructure/`.
- `Infrastructure/` can depend on both.
- A bounded context doesn't import internal classes from another: it communicates via domain
  events or via the shared kernel (`src/Shared/`).

Breaking one of these four rules isn't a stylistic detail: it's the reason the repo is organized
this way. If the work requires it, that's an `ARCH` finding, not a shortcut.

## Mapping and value objects go together

Changing `<Aggregate>.orm.xml` without updating the aggregate and its `<Vo>Type` (or vice versa)
produces a runtime failure that no unit test catches. The three files are touched in the same
commit, or none of them are.

## Formatting: the tool fixes it

Don't reindent, don't reorder imports, and don't change quotes by hand: run the `fix` key from
`commands.md`. A hand-made formatting diff pollutes the review and fights the formatter.
